# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Artonseley: a Spanish-language Node/Express app that lets users search Mexican legal articles by keyword (with synonym matching via a dictionary) or by article number. All code, comments, and user-facing strings are in Spanish — match that when editing.

Not a git repository (no `.git` here). No test suite, no linter, no build step — just Node/Express.

## Commands

```
npm install   # first time, or after package.json changes
npm start     # runs `node servidor.js`, serves on http://localhost:3000 (and on the LAN IP, printed at startup)
```

There is no test, lint, or build tooling in this project.

## Architecture

The core design principle (see README.md) is a strict client/server split: **no legal data or search logic is ever sent to the browser.** The client only renders UI and calls the API.

- **`publico/`** — everything the browser can see: HTML pages with inline `<style>`, `documento.css` / `plataforma.css`, static info pages, and `publico/Sistema/*.js` (client-side ES modules, one entry point per page). This JS has no access to the law data — it only does `fetch('/api/...')` and DOM rendering.
  - **Page structure:** `index.html` is the **home screen** ("burbujas": a random Georgia greeting from `Sistema/frasesBienvenida.js` + rounded-rectangle links). Each area is its own full page, gated by `requiereSesionParaPagina` in `servidor.js`: `buscador.html` (the search UI + entry point `buscadorPrincipal.js`), `editor.html` ("Cuadernos"), `notificaciones.html`, `sugerencias.html` (the old "buzón" form), `configuracion.html` (Mi cuenta / Personalización / links / cerrar sesión), `escritorio.html` (a tiling dashboard — `escritorioPrincipal.js` — where the user drags the areas as resizable `<iframe>` tiles onto a fixed grid; layout persists in `localStorage` under `escritorioLayout`), `pestanas.html` (an in-app browser — `pestanasPrincipal.js` — a Chrome/Edge-style tab strip over one full-screen `<iframe>`; **duplicate tabs of the same area are allowed**, each tab is its own `{uid, appId}`; open tabs + active tab persist in `localStorage` under `pestanasAbiertas` / `pestanasActiva`; "+" opens a dropdown of areas, closing the last tab shows a picker grid), `calendario.html` (`calendarioPrincipal.js`: one month full-screen, per-day encrypted notes + day colors), `musica.html` (`musicaPrincipal.js`: the music player UI), and `calculadora.html` (`calculadoraPrincipal.js`: the "Calculadora Jurídica Financiera"). The area list shared by Escritorio and Pestañas lives in `Sistema/areasDelSistema.js` (`AREAS` / `AREA_POR_ID`); each screen filters out itself. On `index.html` the **Escritorio** and **Pestañas** bubbles are pulled out as two equal-size centered "primary" buttons (`.burbuja-principal` / `.acceso-principal` in `plataforma.css`, fixed 380×120); the rest stay in `.rejilla-accesos`. `buscador.html`'s top bar no longer has the 🔔/⚙️ icons (redundant with the home screen).
  - **Music (`musica.html` + `Sistema/reproductorGlobal.js`):** `reproductorGlobal.js` is the playback engine and is included via a `<script>` tag on **every** session-gated page (index, buscador, editor, notificaciones, sugerencias, configuracion, calendario, escritorio, pestanas) — plus `musica.html`, which loads it through `musicaPrincipal.js`. Once a song or playlist is started it keeps playing across page navigations: state (current track, position, volume, mute, global pause, playlist schedule) is persisted to `localStorage` under `artonseley::reproductor` and each new page resumes from it with a 1 s fade-in that hides the sub-second gap. The engine does **not** run inside an iframe (`window.top !== window.self`) so the Escritorio tiles never double the audio — an iframed page proxies its API calls to `window.top.__reproductorArtonseley`. Web Audio graph: `<audio>` → MediaElementSource → fade gain → volume gain → AnalyserNode (the per-song spectrometer on `musica.html` reads this) → destination. Single song = infinite loop with 1 s fade at each restart; playlist = each entry loops to fill its assigned minutes, 5 s crossfade between entries, and a 10 s fade-out over the final 10 s of the summed total, then it stops (no repeat). Songs are uploaded from `admin.html` (see below). The example seed note in `calendarioPrincipal.js` (`sembrarNotaEjemploSiAplica`) creates a one-time "Ejemplo de nota!" on first vault unlock, guarded by `localStorage` key `calendario::ejemploSembrado::<email>`.
  - **Calendar reminders (Web Push):** `publico/sw.js` (the only service worker; served from `/sw.js` with `Service-Worker-Allowed: /` and `Cache-Control: no-cache`, route in `servidor.js` before `express.static`) + `publico/Sistema/recordatoriosCalendario.js` (client helper) + a toggle in `configuracion.html` ("Recordatorios del calendario"). The user opts in → browser notification permission → `pushManager.subscribe` with the server's VAPID public key → `POST /api/recordatorios/suscribir` stores the subscription + the device's `offsetMinutos`. A server sweep (every 30 min, plus `POST /api/tareas/recordatorios` for an external cron) sends a **content-less** push once a day once it's past 7 AM in that device's local time; `sw.js` shows a **fixed-text** notification (no calendar data — the E2E encryption is untouched, the SW decrypts nothing). `calendarioPrincipal.js` calls `recordatoriosCalendario.sincronizar()` (dynamic import) on load to refresh the subscription / timezone. Needs `VAPID_PUBLICA`/`VAPID_PRIVADA` env vars (`npm run generar-vapid`); without them the feature is off and the site runs normally. `publico/manifest.webmanifest` (linked from `index.html`) is a minimal PWA manifest, mostly for iOS "add to home screen".
  - **Calendar vault:** `calendario.html` has its OWN encrypted vault — `bovedaCalendario.js` + `almacenamientoCalendario.js`, a separate IndexedDB (`artonseley_calendario::<email>`) with its own 12-word BIP-39 phrase — fully independent from the "Mis cuadernos" vault (`manejaBovedaCifrada.js`), so wiping one never touches the other. Both reuse `criptografiaCuadernos.js` for the crypto primitives. The optional "auto-delete notes older than a month" toggle lives in `configuracion.html` and is a per-user `localStorage` flag (`calendario::borradoAutomatico::<email>`), off by default. The side-panel modules (`manejaSugerencias.js`, `manejaBuzonSugerencias.js`, `manejaConfiguracion.js`, `manejaPanelesLaterales.js`) now serve only `editor.html`; the standalone pages use `paginaNotificaciones.js` / `paginaSugerencias.js` / `paginaConfiguracion.js` and `plataforma.css`. `manejaPersonalizacion.js` exposes `aplicarModoGuardado()` (color only) and `renderizarPersonalizacionEn(el)` (inline selector) besides the old floating panel.
  - The user's optional display name (apodo) lives in `usuarios.nombre`; `GET /api/sesion` and `POST /api/login` return it and `POST /api/mi-cuenta` sets it. Empty ⇒ the greeting shows the literal text `[user]`.
  - **Legal pages are NOT static files.** `/terminos-y-condiciones.html` and `/avisos-de-privacidad.html` are generated per-request by `servidor/paginasLegales.js` from two Markdown files at the repo root (`Terminos_y_Condiciones_Artonseley.md`, `Aviso_de_Privacidad_Artonseley.md`) via the tiny converter in `servidor/renderizarMarkdownLegal.js`. Edit the `.md` to change the text; there are no `.html` files for these two in `publico/`. Routes are registered before `express.static` in `servidor.js`.
- **`servidor/`** — everything that stays server-side: the law JSON data (`servidor/datos/`), the synonym dictionary, the letter/prefix matcher, the article-text lookup, and the search orchestration (`procesarBusqueda.js`).
- **`servidor.js`** — Express entry point. Serves `publico/` as static files and exposes:
  - `GET /api/documentos` — list of distinct document names (e.g. "Código Penal", "Ley de Amparo"), used to render the sector/document filter buttons.
  - `POST /api/buscar` — body `{ texto, documentos }` → `{ tipo: 'resultados', resultados, avisos }` or `{ tipo: 'mensaje', mensaje }`.
  - `POST /api/sugerencias` — body `{ mensaje, urgencia }`, appends to `servidor/datos/sugerencias.json` (read-modify-write of the whole file; not a database).
  - `GET /api/sugerencias` — dumps all stored suggestions as JSON (no auth — intended for the site owner to check manually).
  - **Sesiones simultáneas por cuenta:** sessions are DB-backed rows (`sesiones` table, `servidor/db/sesiones.js`), not stateless JWTs — one row per logged-in device, deleted on logout or on expiry. `POST /api/login` counts a user's live rows (`contarSesionesActivasDeUsuario`) against `usuarios.limite_sesiones` (`NULL` → `LIMITE_SESIONES_POR_DEFECTO` in `servidor/config.js`, default 2) and rejects with 409 once the limit is reached — the counter is *derived* from real session rows, never a manually incremented value, so it can't drift or go negative. Admin (`admin.html` → "Usuarios y licencias", per-row "Cambiar límite" / "Cerrar sesiones"): `POST /api/admin/usuarios/:id/limite-sesiones` (`{limite}`, null = default) and `POST /api/admin/usuarios/:id/cerrar-sesiones` both call `borrarSesionesDeUsuario` — changing the limit ALWAYS force-logs-out every device on that account (a deliberate choice: any admin-side adjustment leaves the account in a clean, known state), while a user's own logout only ever removes that one session. See Términos Cláusula 2.7 / Aviso de Privacidad Sección II ("Conteo de sesiones activas") for what is and isn't tracked (a live count only — no timestamps, no per-device identification).
  - **Music:** `GET /api/canciones` (session) lists songs; `GET /api/musica/audio/:id` and `/api/musica/imagen/:id` (session) stream the files with HTTP `Range` support via `res.sendFile`. Admin: `GET/POST/PATCH/DELETE /api/admin/canciones` — `POST` is `multipart/form-data` (handled by `multer`, see `servidor/musicaArchivos.js`), `PATCH` renames (`{titulo}`) or reorders (`{mover:'subir'|'bajar'}`). The `canciones` table (see `servidor/db/conexion.js` + `servidor/db/canciones.js`) holds only metadata; the actual audio/image files live in `CARPETA_DATOS/musica/` (i.e. next to `artonseley.db`, so on the same persistent disk in production). Music requires a session but **not** a valid license, same as the calendar and notebooks.
  - **Calculadora Jurídica Financiera:** `POST /api/calculadora/:tipo` (session + valid license, like `/api/buscar`). All calc logic is server-side in `servidor/calculadoras/` — `registro.js` maps `tipo → módulo` (currently only `'indemnizacion-laboral'`) and re-exports `obtenerIndicesEconomicos` from `servidor/db/indicesEconomicos.js` (the `indices_economicos` single-row table: salario mínimo general / Frontera Norte / UMA). The admin edits those from `admin.html` → "Índices económicos" via `GET`/`PUT /api/admin/indices-economicos` (no restart needed — the DB read isn't cached). While the minimums are 0 the calc route returns `{tipo:'mensaje'}` instead of calculating. Each módulo exports `validar(entradas) → string[]` and `calcular(entradas, indices)`; the response follows `{tipo: 'resultado' | 'errores' | 'mensaje'}` like the search. `indemnizacionLaboral.js` (Fase 1) returns a line-by-line desglose citing the LFT article for each concept; the 2× salario-mínimo cap (Arts. 485-486) is a caller-chosen toggle (`tope2xSM`). Client: `publico/calculadora.html` + `Sistema/calculadoraPrincipal.js` (form → POST → render; no calc logic). Fases 2 (INPC/intereses) and 3 (pensión) plug into the same `registro.js`.
  - **Legal markdown renderer:** `servidor/renderizarMarkdownLegal.js` now skips `<!-- HTML comment -->` lines/blocks, so `Terminos_y_Condiciones_Artonseley.md` / `Aviso_de_Privacidad_Artonseley.md` can carry editor-only "PENDIENTE" notes that never reach the public page.
  - **Generador de Plantillas y Documentos** (`plantillas.html` + `Sistema/plantillasPrincipal.js`): a library of "machotes" (contratos/demandas/…). Only the template text lives on the server (`plantillas` table + `servidor/db/plantillas.js`); it carries `{{marcador}}` / `{{marcador.subclave}}` placeholders. `GET /api/plantillas` (session + license) lists them without the body; `GET /api/plantillas/:id` returns the body plus `variables` derived by `servidor/plantillas/extraerVariables.js` (scans the `{{…}}`, builds a readable label). The client builds one input per variable, then `Sistema/fusionPlantilla.js` does the merge **in the browser** (`fusionar`), shows a preview, and exports via `descargarComoWord` (a `.doc` = Word-compatible HTML Blob, no library) or `imprimir` (`window.print()` on a `#paraImprimir` container with an `@media print` rule). Client/case data never reaches the server — Fase 1 has no storage of it; Fase 2 ("Expedientes") will be a 3rd zero-knowledge vault. Admin: `GET/POST/PUT/DELETE /api/admin/plantillas` (`PUT` bumps `version`), `admin.html` → "Plantillas de documentos". 3 EXAMPLE templates are seeded on first run by `servidor/plantillas/ejemplos.js` (only if the table is empty).
  - **Calendar reminders (Web Push):** `GET /api/recordatorios/clave-publica` (session) → VAPID public key; `POST /api/recordatorios/suscribir` / `/cancelar` (session) store/remove a push subscription in the `suscripciones_push` table (see `servidor/db/suscripcionesPush.js`). `POST /api/tareas/recordatorios` — only exists if `TOKEN_TAREAS` env is set, needs `Authorization: Bearer <TOKEN_TAREAS>`, runs the same daily sweep an in-process `setInterval` runs (every 30 min, started after `app.listen`). The sweep (`servidor/recordatoriosCalendario.js` → `barrerYEnviar`) sends a fixed-payload push to each subscription once its local time passes 7 AM and it hasn't been sent that local day; a 404/410 deletes the dead subscription. The server never sees calendar contents — `sw.js` shows a fixed message. VAPID keys come from `VAPID_PUBLICA`/`VAPID_PRIVADA` (`npm run generar-vapid`); missing keys ⇒ feature disabled, `configurarWebPush()` returns false and the scheduler doesn't start.

### Search pipeline (`servidor/procesarBusqueda.js`)

1. If the whole input matches `PATRON_NUMERO_DE_ARTICULO` (optionally "artículo"/"art" + a number), it's treated as an article-number lookup → `LectorDeJSON.buscarArticuloPorNumero`.
2. Otherwise the input is split on commas into a list of search terms. Each term goes through `identificadorDeLetras.identificarLetras()`, which checks it against every concept + synonym in `diccionario.js`: exact match returns that one word, a partial match returns all dictionary words that start with those letters (typeahead-style), and no match falls back to using the term literally.
3. `LectorDeJSON.buscarArticulosPorGrupos()` finds, per term-group, every article whose `palabrasClave` matches (first tries an exact dictionary *concept* match via `buscarConceptoLegal`, then falls back to substring match against keywords), then intersects the results across groups (comma-separated terms are AND'd together).
4. Article text bodies are looked up separately by id via `lectorDeTextos.js` and formatted into `[Documento: "Número" Título] (coincide con: ...) texto`. The client (`buscadorPrincipal.js`) parses that bracketed header back out with a regex to split it into a card header/body — if you change the format string in `LectorDeJSON.formatearResultado`, update `PATRON_ENCABEZADO_RESULTADO` in `buscadorPrincipal.js` too.

### Law data (`servidor/datos/`)

Each law source is a pair of files: `articulos/<archivo>.json` (`{ articulos: [{ id, documento, numero, titulo, palabrasClave }] }`) and `textos/<archivoTextos>.json` (`{ textos: [{ id, texto }] }`), joined by `id`. Sources are registered in the `FUENTES` array at the top of `servidor/LectorDeJSON.js`.

**To add a new law:** drop its articles JSON in `servidor/datos/articulos/`, its texts JSON in `servidor/datos/textos/`, and add one entry to `FUENTES` — `{ archivo, archivoTextos, etiqueta }`. Both `leyesCache` and the per-file text cache in `lectorDeTextos.js` are populated lazily on first request and never invalidated, so the server must be restarted after adding/editing data files.

Note: `servidor/datos/articulos/leyesAguasNacionales.json` and `servidor/datos/textos/leyesAguasNacionales.json` exist on disk but are **not** registered in `FUENTES`, so that law is currently unreachable through search. Its articles file also uses a bare top-level array instead of the `{ articulos: [...] }` wrapper the rest of the pipeline expects — it would need reshaping before being wired in.

### Document/sector grouping (client-side)

`publico/Sistema/sistemaDeBotones.js` groups the document names returned by `/api/documentos` into UI "sectors" via the `SECTORES` map at the top of that file. Any document not listed there is auto-bucketed into an "Otros" sector, so nothing silently disappears — but new laws should still be added to `SECTORES` for proper grouping. Document names here must match the `documento` field in the articles JSON exactly (including accents/capitalization).

### Other client-side config points

- `publico/Sistema/manejaConfiguracion.js` — `OPCIONES` array drives the ⚙️ dropdown menu (links to static pages, or opens the suggestions panel).
- `publico/Sistema/manejaSugerencias.js` — `NOTIFICACIONES` array drives the 🔔 "modified laws" panel; this is hardcoded content, unrelated to the `/api/sugerencias` mailbox.
- `publico/Sistema/manejaBuzonSugerencias.js` — the actual suggestion-box UI (textarea + urgency level) that POSTs to `/api/sugerencias`.
